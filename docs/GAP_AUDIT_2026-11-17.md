## 残件リストと推奨実施順序

依存関係を考慮した推奨順。各段は「1 Issue」単位を想定。

1. **D1実環境の整備と環境分離**（基盤）
   - 実D1作成、`wrangler.jsonc` に staging / production の `env` 分離と実 `database_id` 設定、migration 適用手順（local → staging → production）の確立。
   - 依存： なし。ただし Cloudflare アカウント操作・本番デプロイは AGENTS.md の規約どおり利用者（Kazuki）の承認/操作が必要。ここが無いと以降は全部ローカル止まりになる。
2. **公開APIの追加： `GET /api/v1/categories` / `GET /api/v1/feed`**
   - Repository層の拡張（CategoryRepository 新設、VideoRepository にフィード候補取得）。DTOは `shared/api.ts` に追加し、内部行を漏らさない。
   - 依存： 1（ローカルD1だけでも先行開発は可能）。
3. **フィードのD1化 ＋ ジャンル選択（初回・プロフィール）**
   - フィードのデータ源を `src/videos.ts` から `/api/v1/feed` へ切替。初回ジャンル複数選択（OR）を実装。検索結果から開く処理の「フィード外は開けない」問題もここで解消。
   - 依存： 2。これで条件1・3・9の本体が埋まる。
4. **端末内状態： clientState ラッパー ＋ 視聴済み/保存/興味なし ＋ フィード純粋関数 ＋ プロフィール画面の実機能化**
   - LocalStorage 単一ラッパー、視聴済み（アクティブ時）・保存・興味なしの保持、未視聴優先＋興味なし除外＋シャッフルの純粋関数化（SPEC §3）。プロフィールにジャンル変更・保存一覧・履歴/保存/興味設定の削除・全削除＋「サーバー側評価は消えない」明記（SPEC §2.5）。保存/興味なしボタンもここ。
   - 依存： 3。条件5と条件7の前半。
5. **評価API： feedback テーブル ＋ `POST /api/v1/feedback` ＋ 役立った/分類違いボタン**
   - migration 追加、匿名クライアントUUID（4のラッパーが管理）、HMAC保存、`UNIQUE(video_id, client_hash, feedback_type)`、入力検証、レート制限と429（SPEC §5）。
   - 依存： 4。条件7の後半。
6. **管理画面 /admin ＋ 管理API ＋ Cloudflare Access ＋ Worker側JWT検証**
   - 動画/ジャンルの登録・編集・有効/無効、YouTube URLからID抽出（既存 `src/player/youtubeUrl.ts` の抽出ロジックを再利用可能）、分類違いの確認一覧。Access は管理者2名のメールに限定し、Workerで署名/issuer/audience/有効期限を検証、未設定時は fail-closed（SPEC §6）。Access のポリシー設定は Kazuki の操作が必要。
   - 依存： 1、2。条件8・9。
7. **利用案内・プライバシー案内 ＋ バックアップ手順と復元テスト**
   - 評価の保持期間・削除依頼窓口を案内に明記（5の実装内容が前提）。D1 Time Travel ＋ 手動SQLエクスポート手順の文書化、復元テスト1回（SPEC §8）。
   - 依存： 5。公開前の最終工程。
8. **完成判定**
   - SPEC §9 の検証項目を通しで実施： 管理画面で無効化→一般画面から消える、未認証の管理API拒否、評価の重複・連投拒否、iPhone Safari 実機確認（Android/PCは可能なら）。
   - 依存： 1–7 すべて。
